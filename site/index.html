Flash-sale checkout backend

FlashBuy never sells a unit it doesn't have

A FastAPI, PostgreSQL and Redis checkout service built around one constraint: thousands of people can hit the same limited stock at once, and the count at the end still has to be exactly right.

Why a flash sale is a hard problem

A flash sale fails in one specific way: thousands of people hit the same SKU in the same second, whether that's a concert on-sale, a restock, or a Black Friday drop. The naive path reads the stock count, then writes an order, then decrements. Two requests can both read "stock is 1" before either writes, and both succeed. The shop sells a unit it doesn't have.

Fixing that read-then-write race is necessary but not sufficient. Once the write path is correct, the database still can't absorb every concurrent checkout at once: connections, lock waits and query time pile up, and the site slows down for everyone, including the people who would have gotten a unit fairly. And a waiting room that's correct but polls for status still falls over at scale, because thousands of clients asking "am I admitted yet?" once a second is thousands of mostly-wasted round trips.

This is the same category of problem commercial virtual waiting-room vendors solve for e-commerce and ticketing sites. FlashBuy is a from-scratch implementation of that category, not a competing product.

How it was built, in the order bugs were actually found

Every phase below is reproducible from the commit history. Nothing here is a summary of what was planned; it's what happened, including the two phases that started broken on purpose.

Phase 1

A checkout that oversells, by design

Read stock → insert order → decrement, no locking. The point was to prove the race condition first rather than assume it away. A script firing 50 concurrent checkouts against stock 10 produced 50 successes and 6 units left in a stock of 10 that should have hit zero at 10 sales: a real, measured oversell.

Phase 2

Row locking, idempotency keys, reservation expiry

SELECT ... FOR UPDATE on the product row, a unique idempotency key per checkout, and a reserved order state that expires if never confirmed. The same 50-concurrent-checkout script against stock 10 now produces exactly 10 successes and 0 oversold.

Phase 3

A Redis waiting room, so the database never sees the full crowd

A per-product sorted set holds tickets; a drip-feed admission loop lets a capped number through per second, rate-limited per buyer and per IP with an atomic Lua token bucket so one client can't occupy the whole line.

Phase 4

Observability and the first honest load test

Prometheus, Grafana and a Locust journey script went in together. A 2,000-user attempt was tried and discarded: the load generator itself maxed out CPU on the laptop running it, so those numbers measured the test tool, not the service. The 500-user run that became the committed baseline was chosen because it's enough to exhaust the stock without that confound.

Aug 30–31

A real capacity limit, found by a stress test aimed at a specific number

Outside feedback on an early write-up pointed at the actual worst case: admission rate × token TTL means up to 2,400 tokens could be outstanding at once. A targeted stress test confirmed it: 21,977 HTTP 503s, almost all from clients polling status once a second against a Redis connection pool that wasn't sized for that.

Sep 5

Status polling replaced with a push: Server-Sent Events

Instead of asking "am I admitted yet?" once a second, clients now hold one SSE connection and get pushed a token the moment it exists. Same 5,000-user stress shape, same TTL math: 503s went from 21,977 to 0. The honest trade-off, disclosed rather than hidden: up to 3,460 held-open connections instead.

Sep 5

Three replicas, one admission leader

Scaled to three horizontally-replicated FastAPI instances behind a Caddy load balancer. All three run the admission loop every tick, but only the Redis lock holder is allowed to admit, so three replicas don't triple the real admission rate to 60 buyers/sec instead of the intended 20.

Oct 4

The bug internal testing didn't find

Phase 5B's chaos tests killed processes outright and always found the system safe. What they didn't try: a leader that freezes rather than dies, then resumes. That gap was pointed out from the outside, by a commenter on the original write-up, not from inside testing. Fix: a fencing epoch, incremented only on a fresh lock acquisition and checked atomically inside the same Lua script that performs the admission write, so a stale, resumed leader can no longer admit with an old lease. Verified with a deterministic regression test and a live container freeze/resume drill: leadership transferred cleanly, zero duplicate orders, zero oversold.

Oct 22–23

Closing the gaps between the code and the story about the code

A resume-readiness pass found three real, unglamorous problems and fixed all three: documentation that didn't link to itself, a test suite that had been running destructively against the live replica stack instead of an isolated one, and an architecture diagram that no longer matched the actual leader-election behavior. Real CI (GitHub Actions, 21 isolated tests on every push) was added the next day.

Oct 29

Trusting nothing, re-verifying everything from a clean clone

Two earlier internal notes about this project's own state disagreed with each other. Rather than pick one, the whole thing was re-verified from scratch: fresh clone, clean rebuild, a real test run, a real fresh Locust run, and an independent Postgres query to confirm the order count by hand instead of trusting Locust's own summary. That pass is also what caught a mislabeled latency figure before it reached a resume.

Architecture

Buyer traffic goes through the waiting room before it can ever take a PostgreSQL row lock. Caddy load-balances across three FastAPI replicas. Every replica runs the admission loop on every tick, but only the current Redis lock holder is allowed to admit, so replicas can't multiply the real admission rate.

What's still missing, on purpose stated plainly

A portfolio project is more convincing with a known-gaps list than without one. Nothing below is hidden in the code; all of it is already in the repo's own docs.

  • No auth on any endpoint. Every route is open. Fine for a load-testing demo, not fine for anything real.
  • Caddy has no upstream timeout. During the Oct 4 freeze/resume drill it kept routing to a frozen replica for about a minute before giving up. The fencing fix made that window safe, not short.
  • Single Postgres instance. No replica, no failover story for the database itself, only for the app layer.
  • java-service is an empty placeholder. The repo is structured for a second-language comparison under the same load-test shape; it hasn't been built yet.
  • Confirm is not a real payment. The checkout flow proves reservation correctness under load, not a payment integration.
